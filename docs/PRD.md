## 0. 文档定位与协作规则

本文件同时承担 **产品需求文档（PRD）+ MVP 范围约束 + 开发验收规格** 的作用：说明为什么做、做什么、做到何种程度，以及如何验收。它不是要求一次性照搬实现的详细技术设计。数据库 DDL、API Schema、组件结构与技术选型细节应在完成代码审计后进一步形成 `docs/architecture.md`、`docs/api.md` 等实施文档。

**对 Codex 的强制要求：**

1. 先阅读本文件、MotionCare README、已有后端 API 文档及实际代码，形成「现有能力 / 可直接复用 / 需修改 / 需新建」清单，再开始改动。
2. **禁止从零重建整个项目。** 以 MotionCare 中已验证的前端、后端、MySQL 模式、Garmin/FIT 数据接入、运动分析、鉴权和测试为基线。除非发现明确技术障碍，不迁移技术栈。
3. 每次只实施一个可验证的阶段。编码前给出方案、受影响文件、数据库迁移和验收条件；完成后运行相关测试并说明结果。不得把整个 PRD 当作单次任务直接完成。
4. 优先保障端到端业务闭环、数据一致性、可解释性和演示稳定性。避免为概念完整而引入多 Agent、复杂工作流引擎、向量数据库或新硬件。
5. 凡本文件的 API、表名、数据字段属于建议，应以实际代码和兼容性审计为准；遇冲突应说明取舍，不能静默删除现有功能。
6. 任何模型输出必须经过服务端校验；模型不得直接执行 SQL、写文件、访问任意 URL 或绕过用户授权调用写入接口。

## 1. 项目背景

MotionCare 是已有的运动数据管理系统，采用 Vue 3 + Vite、Node.js/Express、MySQL，并使用 Python 脚本处理 Garmin Connect 和 FIT 数据。现有能力包括运动记录、路线与时序指标、睡眠与健康数据、训练负荷统计、简单机器学习评分，以及基于运动数据摘要的 AI 对话和每日建议。训练计划前端目前主要使用 `localStorage` 保存，服务端尚缺少计划编排、计划与真实运动的关联及持续修订机制。

SpAgent 的新增价值是：让 AI 教练从「描述运动数据」进一步成为「结合真实运动数据组织训练任务并持续调整计划」的可执行业务 Agent。

本课程重点是**物联网数据技术**。课程答辩必须能够清楚展示：可穿戴设备或 FIT 文件产生数据 → 数据同步/清洗 → MySQL 存储与特征聚合 → Agent 使用数据生成/调整训练计划 → 新运动记录回流形成反馈闭环。

**真实数据来源与演示替代：** 首选已有 Garmin/FIT 记录；无需购买新传感器。由于实时 Garmin 登录、第三方平台或模型 API 可能不可用，必须提供合成、脱敏且可重复导入的演示数据与流程。演示数据须明确标识，不冒充真实采集。

## 2. 产品定位、用户和目标

### 2.1 定位

面向初级至中级跑者的 **数据驱动型个人 AI 跑步教练**。第一版聚焦跑步训练计划，不扩张为通用健康 App 或通用 Agent 平台。

### 2.2 核心用户

- 有跑步记录，想完成首次 5km 或规律训练的初级跑者。
- 已有运动手表数据，希望基于自身负荷与恢复状态合理安排每周跑步的跑者。
- 课程演示者：需要以清晰的可视化流程证明系统真实使用 IoT/时序数据与 Agent 工具调用。

### 2.3 用户问题

- 运动平台能显示大量配速、心率、负荷数据，但用户难以转化为下周具体安排。
- 静态课表难以适应临时没空、漏训、疲劳和恢复状态波动。
- 传统 AI 聊天建议停留在文本，难以保存、执行、追踪和复盘。

### 2.4 MVP 成功标准

用户能够在浏览器中完成一条完整链路：**设定跑步目标 → Agent 读取个人历史数据 → 生成结构化计划草案 → 用户确认保存 → 在训练日历看到计划 → 导入/关联一次实际运动 → 自动生成差异分析 → 申请并确认一次计划调整 → 查看修订记录。**

验收优先级高于界面数量、模型参数数量和算法宣传。

## 3. 范围与非目标

### 3.1 P0：课程设计必须完成

| ID | 模块 | 必须具备的能力 |
|---|---|---|
| P0-01 | 现有系统继承 | 保留登录、运动/健康数据浏览、基本统计与 Garmin/FIT 数据接入；清理只影响演示体验的冗余入口时应保证相关功能不被意外破坏 |
| P0-02 | 数据准备 | 使用已有运动数据查询及特征聚合能力，提供近 7/28 天的跑量、频率、配速、负荷、可用恢复数据与数据质量标识 |
| P0-03 | 跑步目标 | 创建一个目标（首次完成 5km、规律跑步、5km 提升三种模板中至少两种）；设置每周可训练日期与每周次数 |
| P0-04 | Agent 交互 | 对话输入目标/变更请求，Agent 能自主调用**白名单业务工具**读取数据并产生结构化结果；展示执行状态与证据摘要 |
| P0-05 | 训练计划 | 生成适合未来 4 周的计划草案，支持训练类型、日期、距离/时长、强度提示，用户确认后保存到 MySQL |
| P0-06 | 计划管理 | 查看周历与详情、手动跳过/完成训练、保持页面刷新后状态不丢失；每个任务有明确状态 |
| P0-07 | 运动匹配 | 将新的或已有的运动记录匹配到计划任务，计算计划与实际的差异，避免同一运动记录被重复完成多条训练任务 |
| P0-08 | 动态调整 | 允许用户以自然语言修改日期/训练量；系统返回变更前后差异与理由，**确认后**才落库并记录版本 |
| P0-09 | 反馈与追溯 | 展示跑后简短复盘、最近一次调整原因、所参考的数据及调整历史 |
| P0-10 | 演示与测试 | 一键或文档化启动、脱敏样例数据、可重复的主流程演示、关键自动化测试 |

### 3.2 P1：P0 稳定后再考虑

- 一周总结与下周计划候选建议；根据计划执行率自动提出调整请求。
- 跨会话记住用户的明确偏好（固定训练日、训练目标），并提供可查看/删除的设置。
- 更精细的训练分段结构、训练执行趋势图、消息流式显示。
- 活动自动同步后的异步处理任务、通知提醒。

### 3.3 明确排除

- 多 Agent 协作、Agent 自主发起无限循环任务、模型自训练、向量数据库和复杂 RAG 知识库。
- 实时语音跑步教练、实时生理监控、医疗诊断、心电图分析、复杂路径规划或赛事社交。
- Android/iOS 原生客户端重写、云原生微服务重构、Kubernetes、复杂消息队列。
- 以重新开发登录、运动数据、AI 评分为主要工作量。

## 4. 核心产品交互

### 4.1 信息架构

优先维持 MotionCare 原有前端视觉体系，以现有页增量改造：

- **今日**：显示当前训练状态、今天是否有任务、AI 建议与「查看计划」。
- **AI 教练**：对话、工具执行进度、数据依据、计划预览卡片、变更确认卡片。
- **训练计划**：我的计划、周历、任务详情、执行状态、计划版本记录。
- **运动记录详情**：实际运动与对应计划任务的关联、执行差异和简短复盘。

移动端优先兼容手机宽度，桌面浏览器可正常使用。核心能力必须通过页面操作完成，不能只在 API 中存在。

### 4.2 关键用户故事

**US-01 初次制定计划。** 用户输入「我每周二、四、日有空，未来四周想建立 5km 跑步习惯」。系统先查询运动与恢复指标，并明确告诉用户有多少条记录、数据时间范围及缺失项。Agent 生成结构化四周训练草案，以卡片/周历预览；若关键约束不明确，最多询问必要的补充信息。用户确认后创建活动计划。

**US-02 临时更改日程。** 用户说「本周四有考试，把训练调整一下」。Agent 查询当前计划及周内安排，提出修改前后对比。用户点击确认才修改数据库；拒绝或超时不产生副作用。

**US-03 跑后数据反馈。** 用户完成周二跑步并同步 FIT。系统按照用户、时间、运动类型、完成状态进行候选匹配；自动匹配只有在唯一且可信时发生，其他情况由用户手动选择。记录距离、时间、配速等计划/实际差异，并生成简短复盘。

**US-04 恢复状态变差。** 如果可用数据出现近期负荷偏高、睡眠不足等信号，系统能在用户请求或计划回顾时给出保守调整建议。证据不足应说明依据缺失，不能伪造 HRV/睡眠评分或给出医学诊断。

**US-05 模型失效。** 模型 API 中断时，现有数据、计划和记录仍可查看；Agent 提示暂不可用，不出现「已保存」等虚假成功。允许使用现有规则能力生成明确标注为规则建议的基础分析（若实现）。

### 4.3 计划操作原则

- 对话本身不等于已完成的业务操作；**结构化卡片 + 操作状态**才是权威结果。
- 写操作至少经历 `proposed → confirmed/rejected/expired → applied/failed`，支持重试去重。
- 计划生成有草案、已激活、已完成、已归档等状态。限制每位用户默认同时只有一个活动计划，简化 MVP。
- 修改已激活的计划，必须产生可追踪版本。已执行训练的历史记录不可因后续调整被静默覆盖。
- 用户可自主编辑目标和手动调整日程；Agent 不得成为唯一操作入口。

## 5. Agent 产品与技术行为规格

### 5.1 Agent 定义

采用 **单一 Coach Agent + 受限工具调用**，不引入专门多 Agent 框架。模型负责理解自然语言意图、选择工具、组织解释与展示建议；业务逻辑、数据读取、计划校验、写入审批、负荷安全边界由服务端管理。

### 5.2 MVP 工具清单（语义接口，命名可调整）

| 工具 | 类型 | 输入/输出关键点 |
|---|---|---|
| `get_runner_profile` | 只读 | 用户偏好、目标、可训练日、基础运动信息 |
| `get_training_context` | 只读 | 指定用户的 7/28 天训练汇总、恢复指标、数据时间范围、缺失指标与规则/ML 风险摘要 |
| `get_active_plan` | 只读 | 当前计划及任务、版本、已完成情况 |
| `propose_training_plan` | 计算/草案 | 目标与约束 → 标准化、校验后的计划草案，不直接激活 |
| `propose_plan_revision` | 计算/草案 | 原计划 + 用户变更 + 约束 → 结构化 diff、调整理由 |
| `get_activity_summary` | 只读 | 已归属用户的某次运动详情和汇总 |
| `get_plan_execution` | 只读 | 计划任务与实际运动之间的完成情况、差异汇总 |

**写入动作**（如 `confirm_plan`、`confirm_revision`、`link_activity_to_session`）通过后端受控操作 API 完成，默认不直接交给大模型无审批执行。初版可以用上述 7 个工具完成可信的 Agent 演示。

### 5.3 Agent 调用流程

1. 接收带会话 ID 的用户消息，服务端从鉴权上下文确定用户 ID。
2. 模型判断需调用的只读工具，服务端执行并返回最小必要结果。
3. 模型产生意图或草案；**服务端再运行约束检查与规范化**。失败时可要求模型重新修正，重试次数有限。
4. 向前端返回类型化卡片：`text`、`tool_status`、`plan_draft`、`plan_diff`、`error`。不依赖前端解析自由格式 Markdown 来执行命令。
5. 对写入方案创建待确认动作记录；前端向用户明确展示改变内容。
6. 用户确认时调用受保护的后端操作 API，服务端二次检查用户归属、动作状态、计划版本、字段约束和幂等键，再以事务写入。
7. 返回真实执行结果与数据库对象 ID；成功后界面刷新相关计划与日历。

### 5.4 训练计划规则

- 仅生成跑步相关训练，先支持轻松跑、常规有氧、休息/恢复三类训练；速度训练作为扩展。
- 第一版每周 2–4 天、计划周期固定 4 周；根据最近历史训练量或保守新手模板生成初始安排。
- 无历史数据时使用**显式标注为“缺少历史数据的基础模板”**的起步计划，并以较低强度为主。
- 每周训练日必须符合用户设置；同一日默认最多一个计划任务；训练频率及相邻训练间隔由规则检查。
- 不允许模型自由给出大幅增加跑量、无条件高强度训练或以单次数据诊断疾病的方案。
- 完整训练方案应由可测试的模板/规则生成器提供结构，LLM 用于意图识别、参数补齐与自然语言解释，减少格式漂移。
- 训练负荷规则以现有 `coachMlService` 等系统能力为基础；正式阈值与版本以代码审计后确定，避免在 PRD 中伪造医学/运动学“标准线”。

### 5.5 记忆与上下文

P0 只保存会话消息和明确的计划参数。每次调用动态读取 MySQL 中的最新运动/恢复数据，不在 Prompt 中持续累积所有历史记录。服务端限制上下文条数、工具响应尺寸和迭代次数（建议单轮至多 4 次工具调用链，后续按实际评估）。

不需要在 P0 上向量记忆。用户偏好优先保存到现有设置或新增明确字段，并允许编辑。

## 6. 数据层与物联网数据链路

### 6.1 数据管线

`Garmin / FIT 文件 / 脱敏演示文件 → 解析与单位归一化 → 活动/健康时序表 → 7/28 天特征汇总 → Agent 查询工具 → 训练计划决策 → 执行匹配与反馈`

尽量复用 MotionCare 的 `Activities`、`ActivitySummaries`、`TrackPoints`、运动时间序列表、健康摘要、训练状态数据及既有同步接口。

必须处理：时间与时区转换、km/m 和秒/分钟等单位、缺失值与设备差异、重复同步、同一用户的数据归属、异常 GPS/传感器值。数据新鲜度应体现在 Agent 返回信息中。原始样例数据仅使用合成/脱敏数据。

### 6.2 新增表的逻辑建议

下面是**逻辑模型，不是最终 DDL**；字段类型、索引和外键应在技术设计阶段完成。

| 表/实体 | 最小职责 | 关键字段（建议） |
|---|---|---|
| `TrainingPlans` | 存放计划主表及目标 | `id, user_id, title, goal_type, goal_description, availability_json, start_date, weeks, status, version, created_at` |
| `TrainingSessions` | 存放每次计划训练 | `id, plan_id, scheduled_date, session_type, target_distance_m, target_duration_s, intensity_label, status, linked_activity_id` |
| `AgentConversations` | 用户对话线程 | `id, user_id, title, created_at, updated_at` |
| `AgentMessages` | 保存用户与助手文本及结构化卡片引用 | `id, conversation_id, role, content, payload_json, created_at` |
| `AgentActions` | 待审批/已执行的写操作 | `id, conversation_id, user_id, type, payload_json, preview_json, status, expires_at, idempotency_key` |
| `PlanRevisions` | 保存每次确认后的变更差异 | `id, plan_id, from_version, to_version, diff_json, reason, action_id, created_at` |

规则：

- `user_id` 所有权检查必须放在服务端 SQL 查询与事务中，普通用户不可跨用户读取或修改。
- `TrainingSessions.linked_activity_id` 与计划归属同一用户；防止同一活动重复关联冲突。
- `TrainingPlans.version` 用于并发更新冲突检查；确认过期草案后不得覆盖新版计划。
- `AgentActions` 必须有有效期，重复确认不会重复创建计划或重复修改。
- MySQL 正式存储业务状态；`localStorage` 仅用于短期 UI 草稿，不再作为训练计划真相源。
- 使用**增量迁移**，不运行会 DROP 现有用户/运动表的初始 SQL 脚本于实际数据环境。
- 查询与版本记录需要索引；大体量时序数据不放入对话消息表。

### 6.3 数据缺失策略

| 情况 | 系统行为 |
|---|---|
| 无 Garmin 账号/无真实记录 | 提供内置脱敏演示记录，或允许按新手模板生成计划；明确显示数据来源 |
| 有运动记录但无睡眠/HRV | 仅根据真实可用的运动频次、跑量、配速等给出建议；不得补造恢复值 |
| 最近活动过旧 | 在生成计划时提示“数据截至某日期”，不要默认用户当前仍保持旧训练水平 |
| 同步重复文件/活动 | 使用稳定外部活动 ID 或导入指纹去重，确保幂等 |
| 同一次运动可匹配多项计划 | 给用户候选选择，不能静默随机关联 |

## 7. 接口约定（初步）

需在现有 `/api` 规范、认证中间件和统一 `{ data, meta }` 响应风格下扩展，以下为候选 API：

| 方法与路径 | 目的 |
|---|---|
| `POST /api/agent/conversations` | 创建对话 |
| `GET /api/agent/conversations/:id/messages` | 读取会话消息 |
| `POST /api/agent/conversations/:id/messages` | 发送消息，返回文本、工具轨迹和结构化卡片 |
| `POST /api/agent/actions/:id/confirm` | 用户确认，执行受控事务写入 |
| `POST /api/agent/actions/:id/reject` | 用户拒绝待确认动作 |
| `GET /api/training-plans` | 获取我的计划 |
| `GET /api/training-plans/:id` | 计划与任务详情 |
| `POST /api/training-sessions/:id/link-activity` | 手动关联实际运动记录 |
| `GET /api/training-plans/:id/revisions` | 查看修改历史 |

具体路径可以调整，但必须有清晰的前后端接口文档、鉴权测试、参数校验与响应示例。Agent 应复用现有运动查询服务，避免再次实现相同的数据 SQL 逻辑。

## 8. 用户界面验收要求

核心页面最少包括：

1. **目标输入区**：训练目标、可训练日、周频率，可通过自然语言或简单表单填写。
2. **Agent 对话区**：显示用户消息、AI 回答、工具执行状态（如“读取近 28 天运动”“检查训练负荷”），可查看简短的数据依据。
3. **计划草案卡片**：4 周日历/列表，显示日期、类别、目标量、强度说明，提供确认/修改/取消操作。
4. **训练计划页**：查看当天与本周任务、已完成/跳过状态、关联运动记录、下周安排。
5. **计划变更卡片**：列出变更前后的日期/强度/目标量差异，确认后刷新计划，支持历史查看。
6. **运动复盘视图**：从真实活动关联到任务，展示计划与实际的数值差异，并给出简短解释。

UI 设计可以参考开源 Agent 产品的「结构化卡片、执行状态、用户确认」交互，但避免照搬复杂通用工作台。应沿用 MotionCare 的样式体系，不为 UI 重构牺牲业务闭环。

## 9. 非功能与安全要求

- **安全**：所有新增 API 鉴权；Agent 工具默认只读；写入需用户确认；后端统一输入校验、频率限制、SQL 参数化和所有权检查；绝不把密钥或 Garmin 登录凭证传给大模型。
- **隐私**：运动轨迹、健康数据属于敏感个人数据。不得把原始 Garmin/FIT、真实轨迹、手机号、密码、原始共享 SQL 数据包和 `.env` 提交到新公开仓库。向外部 LLM 仅发送完成任务所需的最小汇总，并在 UI 说明云端处理模式。演示时使用脱敏数据。
- **可靠性**：真实数据库提交成功才提示操作成功；接口超时或 LLM 失败时可恢复；重复点击确认不造成重复写入；数据库迁移可复现。
- **可解释性**：所有建议记录最少包括数据窗口、核心依据、所用规则/模型标识、生成时间，缺失项显式可见。不要宣称具有临床诊断能力。
- **可维护性**：依赖尽量沿用当前 Node/Vue/Python/MySQL 体系；业务工具与 Agent 编排分层，提供单元/集成测试与错误日志。
- **性能**：典型个人数据量下，日历与计划页应无需等待 LLM 即可展示；运动时序数据在后端聚合后传给 Agent，避免全量 JSON 注入 Prompt。
- **演示稳定性**：本地 MySQL + 后端 + 前端可启动；提供无需 Garmin 实时登录的演示数据；AI API Key 缺失时应有明确提示，基础计划与已有数据仍可浏览。

## 10. 测试与验收用例

| 编号 | 操作 | 通过标准 |
|---|---|---|
| AC-01 | 按文档初始化并登录 | 原有运动记录、统计页面可用；无生产账号/密钥硬依赖 |
| AC-02 | 用 4 周目标和固定训练日请求计划 | Agent 读取真实/演示数据并产出结构化草案；界面显示来源与缺失数据 |
| AC-03 | 用户尚未确认即刷新页面 | 活动计划未被暗中创建；待确认草案的状态可按设计恢复或失效 |
| AC-04 | 用户确认计划 | 数据库保存计划和任务；刷新/重新登录后仍可查看 |
| AC-05 | 用户要求移动某一天训练 | 出现变更前后对比；拒绝无写入；确认后版本号增加，旧版本可追溯 |
| AC-06 | 导入一次合规 FIT/演示活动 | 对应用户活动进入 MySQL；能够与训练任务关联并显示计划/实际差异 |
| AC-07 | 对同一活动重复同步/重复确认 | 不重复创建活动关联、不重复应用同一动作 |
| AC-08 | 切换到另一普通用户 | 不可访问前一用户的会话、目标、计划、动作与运动数据 |
| AC-09 | 无睡眠数据/无 Garmin/模型 API 不可用 | 页面无崩溃、不造假、不误报保存；可运行非 AI 部分 |
| AC-10 | 冲突：草案生成后计划已被修改 | 确认时返回版本冲突，并请求刷新/重新生成，不覆盖最新状态 |
| AC-11 | 运行后端测试、前端构建 | 关键校验、权限、确认机制、导入去重、运动关联、训练计划 CRUD 测试通过 |
| AC-12 | 课程演示 | 现场完成从 IoT 数据查看到计划生成、审批、执行匹配、修改记录的闭环 |

## 11. 开发阶段与验收门槛

**阶段 0：基线导入与项目审计（先做）。** 将 MotionCare 当前可用源码以**干净快照**引入空的 SpAgent 本地目录/新仓库，保留前后端、必要 SQL/脚本/测试，不携带真实运动数据、Garmin token、密码、`.env`、原始日志、巨大数据库种子包、上传图片或不必要的二进制模型。记录基线来源与 commit SHA。审计已存在的 AI、计划和健康数据模块；先运行原有测试与构建。**门槛：** SpAgent 可启动原有项目，README 说明配置，现有核心接口可用。

**阶段 1：数据与计划基础。** 建增量迁移、计划/任务 API 与周历，接入现有查询/统计与脱敏样例数据。把计划从前端 `localStorage` 主存储迁移为 MySQL；旧数据如需兼容可提供一次性导入。**门槛：** 不依赖大模型即可创建、查看、编辑、激活和保存计划，刷新页面不丢失。

**阶段 2：最小可用 Agent。** 加入单 Agent 工具编排、只读数据查询、基于规则的计划候选生成、结构化返回、工具状态卡和用户审批动作。**门槛：** 能从一句目标描述产出合理草案；用户确认后完成真实持久化；拒绝不写入。

**阶段 3：执行反馈闭环。** 对接 Garmin/FIT 现有活动导入，完成计划任务匹配、计划/实际差异、计划调整提议、版本历史及基础复盘。**门槛：** AC-01 至 AC-12 关键用例通过；有可以重复演示的完整故事线。

**阶段 4（可选）：体验增强。** 周报、图表优化、轻量偏好记忆、流式反馈、部署与展示优化。必须在阶段 3 稳定以后再做。

每阶段提交应包含：代码改动、数据库迁移、README/接口文档更新、相关自动化测试、实际运行验证结果和遗留问题。避免一次提交过大、不易复查。

```text
SpAgent/

├── AGENTS.md                 # Codex 工作约束（基于本 PRD 补充）
```
