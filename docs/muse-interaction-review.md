## 专项观察：点击、转场和等待

逐帧查看了 Meta 发布的 25.73 秒购物演示。以下时间均指发布视频的时间轴，剪辑与示意动画可能改变节奏，画面也没有可靠的手指落点时间。该样本可以用来研究变化顺序。[Muse 官方购物演示](https://about.fb.com/wp-content/uploads/2026/09/Muse_Shopping.mp4)

| 视频位置 | 实际可见的变化 | 值得学习的做法 |
| --- | --- | --- |
| 7.2–7.6 秒 | 7.2 秒仍是聊天列表，7.4 秒详情面板已从底部进入，背景开始变暗。7.6 秒主按钮可见。后方聊天仍在原位 | 打开局部详情时，让内容接着当前界面展开，并保留用户刚看到的上下文。过渡时尽量保持背景和导航稳定 |
| 11.5–13.75 秒 | 细节面板收起后回到原会话，先出现活动指示，随后出现自然语言确认和单独的浏览器状态卡。输入区保留在屏幕底部 | 把操作回执、处理中状态和最终结果作为独立界面状态。用户可从同一位置继续浏览和输入 |
| 约 17–20 秒 | 审批卡直接出现在会话，随后原处展示下一段执行状态 | 让确认和结果延续同一个任务，避免用户离开原位置寻找反馈 |

Muse 的设计团队说明，用户在复杂任务执行期间可以继续发消息和补充指令。设计负责人也描述了用简短反应或初始消息先接住请求，再在同一个状态入口按需展开细节。这与演示中看到的阶段变化吻合。[Muse 团队设计记录](https://muse.ai/blog/how-we-designed-muse) [设计负责人访谈，8:50 起](https://www.youtube.com/watch?v=4TOLm1g-gCE&t=530s)

### 真机测量项目

公开演示可以确认界面如何接续。物理点击到首次亮度、形状或位移变化的延迟，以及触感和滚动跟手，需要在实际设备上测量。测量应固定设备和刷新率，记录设备型号、系统与应用版本，分别测试首次打开和重复操作。建议在真机上用外部高帧率相机同时记录落指和屏幕，有可复现步骤时再用 Android 帧时间工具定位卡顿。

- **按键反馈**：记录手指落下到首个视觉变化的帧数，观察抬手后的恢复、滑出取消和连续点击是否一致。
- **转场与返回**：记录面板首帧和可操作时刻，检查是否有空白帧、滚动位置重置，以及中途返回后能否自然接回。
- **慢请求**：分别记录操作回执、首条可用状态和最终结果。检查等待期间能否滚动、继续输入或返回。

## 可选改版范围

先打通「今天 → 教练 → 计划」三屏。首页首屏优先展示当天真实任务和一个主操作，已完成时给出复盘入口。教练使用可续接的对话与固定输入区，逐步补齐目标、日期、频率和时长；四周草案与修订差异有明确的确认位置。计划页能从链接打开对应任务，刷新恢复选中项。三屏复用现有 Vue、Vant 及计划审批 API。

视觉沿用 SpAgent 的绿和中性色。标题、状态、主要操作建立固定层级；手机用单列，桌面保留可读宽度并利用空余空间。用 4px 间距基准、清晰焦点和约 44px 触控目标。短动效只用于状态反馈及卡片展开，并响应系统减少动态效果设置。

验收时观察 Chromium 窄屏、键盘和中文输入法，以及 Android 实机的软键盘与系统返回。用户应能在状态切换时保持阅读位置，草案确认失败后保留输入和草案，刷新后恢复可操作状态，后台提醒可追溯并可关闭。动态演示仍需用真机或录屏核对。
